# 2026-06-06 — Qwen3.6-27B Quark INT8 multimodal: dual-concurrency @ 40K

Single-VM dual-GPU (TP=2) on the 199 host. Config:
[`servers/vllm/qwen3_6-27b-quark-int8-graph-tp2-multimodal.sh`](../servers/vllm/qwen3_6-27b-quark-int8-graph-tp2-multimodal.sh)
— `max-model-len 40960`, `max-num-seqs 2`, `TRITON_ATTN` ViT, gemv INT8 patch,
cudagraph `FULL_DECODE_ONLY` `[1,2]`, on `/home/ubuntu/vllm-venv`. Recipe +
findings: [`docs/qwen3_6-27b-multimodal.md`](../docs/qwen3_6-27b-multimodal.md).

**Methodology (the correct one):** streaming completions; decode rate is
**TTFT-cancelled** = `(n − 1) / (t_last − t_first)`; `ignore_eos` + fixed 120 tok so
all N streams run full-length and overlap; **a warmup sweep is run and discarded**
(JIT'd batch shapes); unique prompts (no prefix-cache sharing). Aggregate = Σ
per-client decode (matches the repo harness convention).

## Per-client decode + aggregate (text streams, batch-shape warmed)

| N | per-client decode | aggregate | mean TTFT |
|--:|--:|--:|--:|
| 1 | 14.3–14.9 | 14.3–14.9 | ~4.6–5.5 s |
| 2 | 11.85 | **23.7** | ~7.8 s |

- Concurrency **scales**: N=1→2 aggregate **1.65×**, per-stream only **−17 %**
  (14.3 → 11.85). Normal batching — the hybrid GDN model does **not** batch poorly.
- Cross-check vs the archived [`p2p-shm`](../p2p-repro/p2p-shm/RESULTS.md) Quark-INT8
  sweep (smaller context): per-req decode N=1/2 = 15.41 / 12.31, scaling 1.60×.
  This 40K config is within ~5 % across the board → **large context does not hurt
  concurrency**. (N=1 14.3 vs 15.41 is the only ~5 % gap, plausibly the 40K
  block-table per-step overhead + run-to-run jitter.)
- `max-num-seqs 2` is the ceiling here: 4×40960 KV does not fit the 96,548-token
  pool, so N=4 would queue 2-at-a-time, not batch 4-wide.

## Multimodal (end-to-end, incl. ViT encode + video prefill)

| run | tok/s | notes |
|---|--:|---|
| single video (BBB, 200 tok) | 6.63 | end-to-end; bulk is ViT + 3697-tok video prefill |
| 2 concurrent videos (BBB + Jellyfish) | 7.59 (agg) | both correct + isolated, no OOM, `Running: 2 reqs` |

Server-reported generation throughput peaked **22.6 tok/s** during the N=2 video
run (the clean decode aggregate; the 7.59 end-to-end is prefill-dominated/jittery).

## Correction note

An earlier ad-hoc measurement reported N=2 "**9.8 tok/s, concurrency hurts**". That
was a methodology artifact — raw wall-clock `tokens/elapsed` with the multi-second
TTFT (and an early `stop`) folded into the rate, compared against a TTFT-cancelled
single-stream. It is **not** a real regression; the TTFT-cancelled numbers above
(and the server's own 22.6 tok/s) show concurrency scaling normally.
