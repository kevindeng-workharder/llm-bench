# 2026-05-25 — cross-VM IB-P2P TP=2 vs single-VM Infinity Fabric P2P

Same Qwen3-4B FP16 workload, two transport topologies on the same 199 host:

- **Baseline** (2026-04-27 sweep, `vllm-qwen3-4b-fp16-graph-tp2`): both GPUs
  inside one QEMU guest, TP=2 over PCIe + AMD Turin Infinity Fabric.
- **Cross-VM IB-P2P** (`vllm-qwen3-4b-fp16-graph-tp2-IBP2P-final`): one GPU per
  QEMU guest, TP=2 over Mellanox CX-7 dual-port RoCE/IB
  (`roceP3p1s0`, 10.99.0.1 ↔ 10.99.0.2, RDMA verbs via `NCCL_NET=IB`).

vLLM config identical across both: `--max-model-len 4096 --max-num-seqs 8
--max-num-batched-tokens 2048 --gpu-memory-utilization 0.85 --tensor-parallel-size 2
--distributed-executor-backend mp --no-enable-prefix-caching
--disable-custom-all-reduce` + cudagraph capture sizes `[1,2,4,8]`,
`FULL_DECODE_ONLY` mode, `temperature=0`, `max_tokens=80`, unique prompts per
client.

## Read

- Cross-VM IB-P2P costs **6–12 %** vs same-host Infinity Fabric. Single-client
  (N=1) takes the largest hit (−12.5 %) because the per-token TP all-reduce
  count is fixed and serialised; for Qwen3-4B's 32 decoder layers, each token
  requires ~64 NCCL all-reduces (attention out + FFN reduce per layer). On IB
  these are ~50 µs/AR vs ~10 µs/AR on Infinity Fabric, so the extra ~2.5 ms /
  token shows up directly in single-stream latency.
- N=2 and N=4 narrow the gap to ~6 % because the AR cost is amortised over
  larger batches and the workers spend more time on compute.
- N=8 reopens the gap (~10 %) — scheduler queuing, KV-cache fragmentation, and
  the partial cudagraph coverage all start to matter at saturation.
- Throughput scales 5.97× from N=1 → N=8 (cross-VM), comparable to the
  baseline's 5.82×. The cross-VM transport does **not** flatten the curve at
  this concurrency.

## Reproducing

Cross-VM setup (one-shot per host boot):

```bash
sudo /home/ubuntu/setup-vfio-2vm.sh                   # bind GPUs + 2 NIC ports
nohup /home/ubuntu/start_vm1.sh > /home/ubuntu/vm1.log 2>&1 &
nohup /home/ubuntu/start_vm2.sh > /home/ubuntu/vm2.log 2>&1 &
# (each VM): sudo bash /tmp/vm_boot_setup.sh 10.99.0.{1,2}/30 enP3p1s0np{0,1}
```

vLLM launch:

```bash
# VM1 (rank 0, leader, API server):
bash /home/ubuntu/start_vllm_xnode_vm1.sh
# VM2 (rank 1, headless follower):
bash /home/ubuntu/start_vllm_xnode_vm2.sh   # uses `vllm serve --headless`
```

Bench:

```bash
ssh -p 2224 -L 8000:127.0.0.1:8000 -fN ubuntu@127.0.0.1
cd /home/ubuntu/llm-bench-work
for N in 1 2 4 8; do
  python3 -m runner.bench -u http://localhost:8000 -m qwen3-4b \
    -n $N -t 80 -T 0.0 --unique \
    --config-name vllm-qwen3-4b-fp16-graph-tp2-IBP2P-final \
    -o results/raw/ibp2p-final-N${N}.json
done
```

Warmup pass (run the sweep once and discard) is required — first-touch Triton
JIT for `_compute_slot_mapping_kernel` and `kernel_unified_attention` adds
~10–20 s to the first request at each new batch shape.
